# InferenceTimeRTC 调参与异常排查指南

适用于本仓库的独立 RTC 入口，当前重点是 π0.5、50 步动作块、30 Hz 双臂 PiPER。

## 0. 当前状态：先停机排查

已经报告抖动和撞击桌面的现象。此时应先使用机械臂急停或断使能，并停止 RTC 客户端，暂停带机械臂的参数试验。`Ctrl+C` 停止发送新指令，但默认 `disable_on_disconnect=false`，不能替代硬件急停，也不保证撤销已经发送的目标。

之前的 `inference_delay=22 / execution_horizon=30 / queue_threshold=35` 来自模拟观测的时延与队列测试，只能说明当时未出现队列耗尽，未证明真实运动安全或优于原版异步。现在将其视为历史时延配置，而非实机推荐值。

当前执行链没有工作台碰撞检测、末端高度保护或完整速度/加速度约束。动作值有限、网络连通、队列非空，都不能证明动作安全。

重点记录以下字段：

| 字段 | 含义 |
| --- | --- |
| `latency` | 相机读取、拷贝、序列化、网络、模型处理到客户端收到结果的总耗时 |
| `estimated_delay` | 本次传给模型的预测延迟，单位为控制步 |
| `actual_delay` | 接收时实际丢弃的已过期控制步，冷启动为 0 |
| `queue` | 新动作块切换后剩余的动作数量 |
| `prefix_steps` | 请求时实际送给模型的旧动作剩余长度 |
| `effective_horizon` | 引导截止位置被实际前缀长度裁剪后的值 |
| `server_policy_device` / `server_device` | 真正选择的服务端设备 |
| `max_abs_overlap_delta` / `joint` | 换块时同一未来时刻的新旧目标最大差及对应关节；不是实际运动幅度 |

这些是时序诊断日志，不是完整关节轨迹。碰撞排查还需要目标关节、实际关节、末端位姿和图像时间等记录。

## 2. 为什么可能不如原版异步

1. 原版异步默认对重叠动作做 `0.3 × 旧动作 + 0.7 × 新动作` 的平均。本 RTC 客户端按时序替换未来动作，不再做该平均。直接对比同时改变了引导和队列策略，不能全部归因于某个 RTC 参数。
2. 固定 22 步是偏向网络尾部的估计。历史模拟测试中，实际延迟中位数只有 13 步、P95 为 16 步。过大的估计会让新块更强地依赖本可更新的旧轨迹；过小的估计也会使引导与实际执行时间不一致。需要当前日志确认，不能将历史分布当作本次抖动的直接证据。
3. `execution_horizon=30` 不代表每执行 30 步重新推理。本实现将它用作前缀权重的截止位置。混淆这个含义会导致错误调参。
4. 队列耗尽时，当前客户端暂停下发目标，继续采集观测和推理。后续动作块仅写日志。无需等到队列耗尽，换块目标差也可能产生跳变。
5. 当前核查还发现了引导梯度路径问题，见第 7 节。此问题应先修正并离线验证，不能靠盲目增大引导权重来补偿。

RTC 在论文中的收益依赖正确的时序和引导实现，并不保证任意部署、模型及任务都优于现有异步策略。[原论文](https://arxiv.org/html/2506.07339v1)

## 3. 公平对照：先固定条件

每轮固定同一 checkpoint、任务文本、相机映射、状态/动作单位、标定设置、GPU、模型精度、去噪步数、控制频率和初始状态。应先用录制观测或离线回放，禁止为做对照而重现砸桌动作。

不要为使报警消失而任意改变 `fps`。控制频率应与训练和既有部署相容；更改它会改变动作执行速度及全部步数的物理时间。

记录原版异步的成功率、单步关节变化、动作块交界跳变、完成时间和时延。任务成功率及运动约束应优先于“看起来更连续”。

本 RTC 入口目前不接受 `--rtc.enabled=false`。不能用它作为同一调度器下的无引导对照。对算法原因作判断时，需要另外构造保持队列策略不变的离线对照；切回原版异步属于整套系统对照。

## 4. 核心参数的联动

记动作块长度为 `C`，预计延迟步数为 `D`，配置的引导截止为 `H`，请求时旧前缀长度为 `L`，请求阈值为 `Q`。

```text
D = ceil(当前版本的稳态端到端延迟 × fps)
实际引导截止 H_eff = min(H, L)
模型中的权重为 1 的前缀范围约到 D
软过渡范围约为 max(0, H_eff - D)
```

`D` 是轨迹引导用的延迟估计，实际丢弃动作由 `actual_delay` 决定，两者不是同一个开关。权重为 1 也不等于硬性安全约束。

| 参数 | 增大的主要影响 | 调试原则 |
| --- | --- | --- |
| `inference_delay` | 更多前缀被高权重约束 | 根据当前数据估计，既不要一味取最大值，也不要为加快反应任意缩小 |
| `execution_horizon` | 扩大对旧前缀的引导范围 | 与 D 一起看；先确保 `H_eff > D`，不要把它当请求周期 |
| `queue_threshold` | 更早请求下一块，可能增加请求频率 | 解决时序余量；不是越大越平滑，也不能突破模型吞吐限制 |
| `max_guidance_weight` | 提高部分去噪阶段的引导上限 | 优先离线扫描较小值，不从碰撞配置向上猛加 |
| `prefix_attention_schedule` | 改变重叠区的权重分布 | 先固定 EXP；其他项稳定后才单独比较 LINEAR |
| `auto_delay` | 自动或固定延迟策略 | 诊断阶段先固定，便于每轮可比；稳定后再评估自动模式 |
| `latency_window` | 改变自动估计的时间窗口 | 仅自动模式有效，不是安全余量，也不是毫秒 |

代码要求 `0 <= D < H <= Q < C`。此外，还要观察真正的 `L`：前一块到达时已经丢弃若干步，下一次请求不一定拥有 Q 步旧前缀。若 `H_eff` 经常被裁剪，应先处理时延/吞吐，而不是继续增加 H。

当 C=50 且长期每次推理耗掉接近 25 步时，连续请求也几乎没有缓冲余量；提高 Q 无法解决这个限制。不要用仅满足“延迟小于 50 步”来判断可运行。

## 5. 离线调参顺序

以下为离线候选范围，未验证为你的机械臂安全参数，不能直接用于恢复当前实机。

1. **先验证实现和动作含义。** 新版本数学检查通过后，用录制观测检查相机顺序、关节顺序、单位、归一化/反归一化、动作索引和目标范围。若目标跳变仍明显，停止参数扫描并定位实现或模型问题。
2. **重新测量 D。** 修正梯度后计算量会变化，需要重新采集当前版本的时延；旧的 461 ms、P95 564 ms 不能直接沿用。GPU 或负载变化也应重测。
3. **固定时序后扫描引导强度。** 先保持 EXP 和相同 D/H/Q，仅比较 `0.1 → 0.25 → 0.5 → 1.0`。这些是候选值，不是递增越大越好。已经出现碰撞时，不应直接试 2、5、10。
4. **再比较引导范围。** 在时序可行的前提下，从 `H = D + 4～6` 的离线候选开始，观察边界跳变和对新观测的响应。Q 可先取 H 加约 4～6 步，但必须小于 C，并核对实际 L；无法满足时先改进时延。
5. **最后才比较自动延迟或权重策略。** 当前自动模式取最近窗口的 P95 并向上取整，不额外加安全步；固定模式的 D 不会在自动模式下作为下限持续生效。

若重新测得当前 D 约 17 步，一个离线时序候选可取 H=23、Q=29；先在同一组录制观测上比较 G=0.1、0.25、0.5、1.0。这里的 D=17 只是说明方法，不能据此改动正在运行的机器人。

每轮只改一项，保存参数、日志、目标关节变化及结果。先筛除不满足运动约束的候选，再比较任务效果。没有队列耗尽不作为单独的通过标准。

论文也指出过高的引导上限会增加不稳定与突兀动作，不能把提高权重当成通用平滑器。[论文附录 A.2](https://arxiv.org/html/2506.07339v1#A1.SS2)

## 6. 按症状定位

| 现象 | 优先检查 | 不应立即做的操作 |
| --- | --- | --- |
| 队列空、停顿后启动 | 推理尾延迟、吞吐、实际前缀余量 | 直接提高引导强度 |
| 队列不空，但换块跳变 | 引导实现、时间索引、目标范围、原版平均策略差异 | 不断增大 Q |
| 修正慢、沿旧轨迹继续走 | D 是否明显高于实际、H/G 是否过强 | 把 D 直接降到任意很小值 |
| 抓取/交接失败但轨迹连续 | 任务、输入映射、模型精度、反馈时序、引导是否过强 | 仅以视觉平滑判断成功 |
| 目标异常、撞桌或越界 | 立即停机，查轨迹、单位、索引和工作空间约束 | 继续带机械臂扫描参数 |

## 7. 本次实现核查与修正范围

共享 RTC 代码原先先计算 `v(x)`，随后才对输入开启梯度。因此，计算 `x - t*v(x)` 的导数时没有包含去噪器对输入的导数。原论文的引导项包含该向量—雅可比乘积。[原论文公式 2 与算法 1](https://arxiv.org/html/2506.07339v1)

CPU 解析例子 `v(x)=0.5x, t=0.5` 中，共享旧实现的首步速度为约 1.8，包含完整输入导数后的结果为约 1.475。这确认了计算差异，但尚不能证明它是这次砸桌的唯一原因。

独立 RTC 入口现通过私有处理器在去噪前开启输入梯度；其他推理入口与共享 RTC 文件保持原样。本版本使用协议 v3，客户端和服务端需一起更新并重启；仅更新客户端日志不能修复旧服务器上的计算。

修正已通过解析梯度测试，并用真实 NFS 模型、GPU 4 和模拟观测完成 12 次无机器人请求验证。该小样本中，热身后端到端约 0.66～0.77 秒，服务端流水线约 0.48 秒；完整梯度引导增加了计算开销。它只验证数值与运行链路，不证明任务或运动安全，也不是新的稳定时延分位估计。50 步、30 Hz 下的缓冲余量更紧，应先重新评估吞吐，不能把 D 无限增大来掩盖问题。

可在没有连接机器人的环境运行数学与队列测试：

```bash
python -m pytest tests/inference_time_rtc tests/policies/rtc
```

这些测试不证明轨迹安全。真实运动恢复前，仍需用记录数据完成轨迹约束与时序核验，再由操作者在受控条件下验证；出现触碰或异常跳变立即终止。

## 8. 实际跳变日志与新增中止条件

`rtc_client_20261118_104234_601983.log` 中的配置为 D=22、H=25、Q=35。请求 1 实际延迟 29 步，超过有效截止 25；请求 2 只有 21 步旧前缀，但结果 27 步后才到，出现约 0.20 秒的队列空窗。请求 3 的软过渡区仅 1 步，后续为 3 步。逐次结果、服务端耗时核对和限制见 [RTC 动作跳变日志分析](rtc_jump_analysis_20261118.md)。

动作开始下发后，一旦队列耗尽，客户端记录 `RTC action queue exhausted` 并暂停下发。已在途的结果仍记录，随后的新观测使用无前缀推理，结果标为 `RTC inference-only result`。在耗尽前，超过 `min(H, L)` 的续推块是否允许换块由 `--allow_late_splice` 控制。换块日志中的 `max_abs_overlap_delta` 表示同一未来时刻的新旧目标差值。

本次 Linux 隔离测试使用模拟模型与机器人，共 192 项通过、3 项 CUDA 测试跳过。测试包括日志中的 29/25 与 27/21 失配、拒绝更新时保留原队列、队列耗尽后不自动恢复，以及首块等待与首块到达的并发边界。停止后续命令不保证撤销已经发出的目标，仍需硬件急停或人工断使能。
